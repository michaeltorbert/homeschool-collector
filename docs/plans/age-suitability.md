## 1. Freeze contracts and synthetic test cases first

Create pure src/age.ts for profile validation and civil-date interval arithmetic; src/ageEvidence.ts for a narrow versioned deterministic extractor. Integrate src/domain.ts, src/decisions.ts, server/schema.sql, server/store.ts, server/index.ts, src/main.tsx, limited styles and meaningful tests. Keep scoring, acquisition, calendar and recurrence support unchanged.

AGE-001 — Profile: optional unknown, exact Gregorian birthday, birth-month/year, birth-year, or integer age-in-completed-years as of an explicitly displayed civil date. Default editor choice is age/as-of, so a birthday is unnecessary. No names or grade guessing. Validate discriminated fields, impossible/future birth dates, plausible documented child domain 0–25 (a product input limit, not provider eligibility), unsupported IDs and extra fields. Precise arithmetic handles age-as-of subtraction/leap boundaries as a set of feasible birthdays, never an invented birthday. Every profile revision records a validated creation/anchor civil date in America/New_York, never host timezone. Month/year and age-as-of feasible birthday sets truncate at that immutable anchor, not at each later evaluation day; contradictory/future input is rejected against that anchor. Identical revision and fixed provider reference yield identical assessment across evaluation dates. Profile updates have immutable local revision, expected-current revision and idempotency; persisted privately with separate endpoint. Ordinary partial settings saves cannot clear it.

Use date-only integer arithmetic. Supported explicit cutoff dates use unambiguous calendar forms; supported explicit first-meeting/event-start wording needs a known single event and supported source-local reference. Missing cutoff can show an event-start provisional comparison, never confirmation. February 29 anniversary interpretations February 28/March 1 both apply unless supported provider wording disambiguates: confirm only when all feasible birthdays and interpretations agree. Age-at-fixed-future-cutoff does not change when today's birthday passes. Unknown profile remains valid.

AGE-004 — Source evidence: retain literal provider rules, inferred audience hints, supervision/role conditions and parent fit corrections separately. Exact quote/span, representation part/content hash, source version, parser revision and reference quote/date accompany every executable rule. Quote presence proves provenance, not semantics. Only narrow documented participant grammar supports executable completed-year inclusive/exclusive bounds; isolated N+, ambiguous roles, ambiguous dates/units/multiple ranges stay unsupported. Preschool/teen/family/all-ages hints carry no invented numeric bounds; all-ages wording does not prove enjoyment. Under-age adult accompaniment never becomes adults-only. Preserve raw unsupported wording and every source representation; display ordering establishes no authority. Silence in another feed is incomplete corroboration, not contradiction or endorsement; contradictory applicable rules/cutoffs remain unknown. Unrelated source conflicts still retain existing warnings.

AGE-006 — Recurrence: a supported program-wide fixed cutoff may be compared against the child and described as meeting/outside that stated AGE RULE only. Unsupported recurrence still leaves session availability, first-meeting references and overall attendance unknown. No occurrences or mandatory attendance invented. Multiple session references or mixed roles with unresolved applicability remain unknown.

## 2. Compare rule status separately from fit

For supported literal rule+actual reference, all feasible ages satisfy => meets stated age rule; all violate => outside stated age rule; overlap => unknown/needs checking. Missing cutoff => provisional even if far outside at event start. Unsupported evidence, profile, reference or conflict => unknown. Audience hint => source-described likely audience separately, no numeric age or automatic admission exclusion. Parent fit label does not alter provider evidence. No numeric fit score or ranking change this increment.

Only confirmed outside maps to Age fail and age-based Excluded placement. Meets means one stated rule only, never overall eligible. Labels identify provider rule status and evidence, likely audience and Your fit correction separately. New/Needs checking/Excluded remain accessible; critical attention remains independently visible.

## 3. Persist private profile and fit intent safely

AGE-009 — Transactional schema migration seeds unknown only for a new profile. Preserve every existing settings/decision/bookmark/review/feedback value. Copy any non-null legacy settings.birthDate into a private pending-legacy record inside the migration transaction before changing settings handling. Preserve original raw value there until explicit local confirm/discard; ordinary settings saves cannot erase it. Flag pending data without echoing it into item snapshots and offer deliberate local profile editor confirmation. Valid user-confirmed input becomes a new profile revision; malformed legacy input remains repairable, never silently normalized. Deprecate settings birthday as an age authority. Separate profile endpoint is guarded by existing loopback/same-origin JSON rules; responses no-store.

AGE-008 — Extend existing wrong-fit reason with optional fitDimensions too-young/too-old/other. Existing wrong-fit commands and history stay valid; absence remains generic wrong fit. Conditional canonicalization must preserve pre-upgrade idempotency receipts exactly. A new decision freezes shown source version and profile revision plus relevant age evidence/assessment revision (no birthday or low-entropy birthday hash). Child/listing scope only. Mixed reasons keep separately explicit general intent; fit itself never creates topic negative or learning. Existing supersession and exact Undo restore earlier fit corrections; no standalone fit-without-pass action this increment. In UI selecting wrong-fit may optionally clarify why; category still suffices and note remains optional. Parent too-young/old never becomes medical/readiness diagnosis.

AGE-007 — Show anyway is reversible household/item age-display override, separate append-only history and idempotent command, with evidence/profile basis. It only bypasses the age placement rule: it cannot override Hide, pass, cancellation or other failed configured rules; active filters may still limit the current view. Material basis change makes override inactive and exposes a visible explanation in attention/details, while history and pending notices persist. It never alters provider rule, source review or fit feedback.

AGE-003 — Add separate age reconsideration evidence key binding active fit decision, shown/current rule evidence, profile revision, reference and algorithm revision. Material age/profile/reference changes may prompt reconsideration while the pass stays active; acknowledgement binds exact key. Attendance/source review cannot acknowledge age reconsideration, and vice versa. Full assessment identity retains profile/extractor revisions for audit and reproducibility; material attention/reconsideration/override signatures instead bind applicable normalized rule semantics, roles/references/conflicts and per-rule comparison/status. A profile refinement that changes only precision/possible-age explanation but leaves the applicable rule outcomes unchanged does not re-prompt or lapse Show anyway. No-op formatting/equivalent quotes likewise do not create age re-prompts, while ordinary exact source review still tracks actual source version. Raw birthday or birthday-interval hashes are not put in decision snapshots. A material rule/reference change is different even if the final comparison remains outside. Current-day change alone never triggers fixed-reference reconsideration. Recompute assessments without creating source versions or automatically Undoing passes.

AGE-002 — Material provider age-rule/reference changes get critical notices for previously surfaced/saved items using existing creation-time notice eligibility. Provider source-version differences generate exact source/change-ID age notices. Calendar parser corrections that actually produce a new normalized source version keep their existing parser cause. An age-extractor/assessment revision computed from unchanged stored source does not invent a source version/change ID or source notice: record a separate local-assessment attention item keyed to the exact old/new material assessment signature, labeled extraction/algorithm correction, for previously surfaced/saved items. It persists independently of filtering/pass/Hide and has its own exact acknowledgement. Fit-decision age reconsideration is separate and is not the only visibility path; saved items without a fit pass still receive material correction attention. Profile edits are local assessment changes, never source notices. Narrow trigger to executable age facts/applicability/reference or loss/conflict of formerly applicable evidence, not every incidental age word. Source correction, confirmed exclusion, Show anyway lapse and later Hide/pass cannot suppress pending critical attention. Review remains exact source/change IDs. Added age notices are an intentional extension of criticality; existing notice retention invariants remain.

Assessment identity binds representation/source-version content, profile revision, extraction/assessment revision and actual reference/evaluation date where relevant. Compute on read first rather than adding a cache prematurely. Snapshot/profile exposure is minimal: profile fields needed only by Preferences; item assessments reference revision IDs. Stale dialog shows pinned source and assessment evidence; profile revision races require explicit reload, drafts survive polling.
